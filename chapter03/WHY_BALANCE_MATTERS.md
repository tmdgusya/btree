# 왜 트리 균형이 중요한가: 파일 시스템 관점

## TL;DR
불균형한 Binary Search Tree는 **높이가 N에 가까워져서** 탐색 시 **N번의 디스크 I/O**가 발생합니다.
균형잡힌 트리는 **높이가 log N**이므로 **log N번의 I/O**만 필요합니다.

**실제 차이: N=10,000일 때, 불균형 트리는 최악 10,000번 I/O vs 균형 트리는 최대 14번 I/O!**

---

## 1. Binary Search Tree의 기본 구조

### 메모리 vs 디스크 저장
```
메모리 기반 BST:
- 노드가 메모리에 연속적으로 존재
- 포인터 접근은 매우 빠름 (나노초 단위)
- 불균형해도 상대적으로 큰 문제 안 됨

디스크 기반 BST (우리의 구현):
- 각 노드가 파일의 다른 오프셋에 저장
- 노드 하나 읽을 때마다 디스크 I/O 발생
- 디스크 I/O는 매우 느림 (밀리초 단위)
- **불균형하면 재앙!**
```

## 2. 순차 삽입의 문제: 파일에서 무슨 일이 일어나는가

### 시나리오: 0, 1, 2, 3, 4, 5를 순서대로 삽입

```
파일 구조:
┌────────────────────────────────────────────────────────┐
│ Header (24 bytes)                                      │
├────────────────────────────────────────────────────────┤
│ Node 0: value=0, left=NULL, right=offset_52          │ <- offset 24
├────────────────────────────────────────────────────────┤
│ Node 1: value=1, left=NULL, right=offset_80          │ <- offset 52
├────────────────────────────────────────────────────────┤
│ Node 2: value=2, left=NULL, right=offset_108         │ <- offset 80
├────────────────────────────────────────────────────────┤
│ Node 3: value=3, left=NULL, right=offset_136         │ <- offset 108
├────────────────────────────────────────────────────────┤
│ Node 4: value=4, left=NULL, right=offset_164         │ <- offset 136
├────────────────────────────────────────────────────────┤
│ Node 5: value=5, left=NULL, right=NULL               │ <- offset 164
└────────────────────────────────────────────────────────┘

트리 형태:
    0
     \
      1
       \
        2
         \
          3
           \
            4
             \
              5

높이: 6 (N과 같음!)
```

### 값 5를 검색할 때 디스크 I/O:
```
1. Seek offset 24  → Read Node 0  → 값 0 < 5, 오른쪽으로
2. Seek offset 52  → Read Node 1  → 값 1 < 5, 오른쪽으로
3. Seek offset 80  → Read Node 2  → 값 2 < 5, 오른쪽으로
4. Seek offset 108 → Read Node 3  → 값 3 < 5, 오른쪽으로
5. Seek offset 136 → Read Node 4  → 값 4 < 5, 오른쪽으로
6. Seek offset 164 → Read Node 5  → 값 5 발견!

총 I/O: 6번 (Seek 6번 + Read 6번 = 12번의 디스크 작업)
```

**문제: N개 데이터에서 최악의 경우 N번의 I/O → O(N) 시간 복잡도**

## 3. 랜덤 삽입의 효과: 균형잡힌 트리

### 시나리오: 3, 1, 5, 0, 2, 4 순서로 삽입

```
파일 구조:
┌────────────────────────────────────────────────────────┐
│ Header (24 bytes)                                      │
├────────────────────────────────────────────────────────┤
│ Node 3: value=3, left=offset_52, right=offset_80     │ <- offset 24 (root)
├────────────────────────────────────────────────────────┤
│ Node 1: value=1, left=offset_108, right=offset_136   │ <- offset 52
├────────────────────────────────────────────────────────┤
│ Node 5: value=5, left=offset_164, right=NULL         │ <- offset 80
├────────────────────────────────────────────────────────┤
│ Node 0: value=0, left=NULL, right=NULL               │ <- offset 108
├────────────────────────────────────────────────────────┤
│ Node 2: value=2, left=NULL, right=NULL               │ <- offset 136
├────────────────────────────────────────────────────────┤
│ Node 4: value=4, left=NULL, right=NULL               │ <- offset 164
└────────────────────────────────────────────────────────┘

트리 형태:
        3
       / \
      1   5
     / \  /
    0  2 4

높이: 3 (log₂(6) ≈ 2.6에 가까움!)
```

### 값 4를 검색할 때 디스크 I/O:
```
1. Seek offset 24  → Read Node 3  → 값 3 < 4, 오른쪽으로
2. Seek offset 80  → Read Node 5  → 값 5 > 4, 왼쪽으로
3. Seek offset 164 → Read Node 4  → 값 4 발견!

총 I/O: 3번 (Seek 3번 + Read 3번 = 6번의 디스크 작업)
```

**개선: 같은 데이터에서 3번의 I/O → O(log N) 시간 복잡도**

## 4. 실제 성능 차이: 디스크 I/O 시간

### 디스크 I/O 비용 (일반적인 HDD 기준)
```
Seek Time:   5-10ms (디스크 헤드 이동)
Read Time:   0.1-1ms (데이터 읽기)
합계:        약 6-11ms per I/O

SSD는 빠르지만 여전히 느림:
Seek:        0.1ms
Read:        0.05ms
합계:        약 0.15ms per I/O
```

### N=10,000일 때 실제 소요 시간 (HDD 기준)

**불균형 트리 (순차 삽입):**
```
높이: ~10,000
최악 검색 I/O: 10,000번
소요 시간: 10,000 × 6ms = 60,000ms = 60초!
```

**균형 트리 (랜덤 삽입):**
```
높이: ~14 (log₂(10,000) ≈ 13.3)
최악 검색 I/O: 14번
소요 시간: 14 × 6ms = 84ms
```

**차이: 714배!**

```
- 트리 높이: ~14
- 매 검색마다 평균 ~10번 노드 방문

성능 차이: 307배
```

## 6. 왜 삽입도 느려지는가?

### 불균형 트리의 삽입 (순차)
```
값 9999를 삽입할 때:
1. Root(0)부터 시작
2. 9999 > 0, 오른쪽 자식으로
3. 9999 > 1, 오른쪽 자식으로
4. 9999 > 2, 오른쪽 자식으로
...
9999. 9999 > 9998, 오른쪽 자식으로
10000. NULL 발견, 새 노드 생성

총 I/O: 9,999번 Read + 1번 Write
```

### 균형 트리의 삽입 (랜덤)
```
값 9999를 삽입할 때:
1. Root부터 시작
2. 비교하며 왼쪽/오른쪽 선택
...
14. NULL 발견, 새 노드 생성

총 I/O: ~14번 Read + 1번 Write
```

**N개 삽입 시:**
- 불균형: O(N²) - 각 삽입이 O(N)
- 균형: O(N log N) - 각 삽입이 O(log N)

우리 실험에서 N=10,000:
- 불균형 삽입: 88초
- 균형 삽입: 296ms
- **차이: 297배!**

## 7. 파일 시스템 관점의 추가 문제들

### 문제 1: 캐시 미스
```
불균형 트리:
- 노드들이 파일에 선형으로 배치
- 다음 노드가 항상 멀리 떨어져 있음
- OS 페이지 캐시 효과 거의 없음

균형 트리:
- 노드들이 여러 레벨에 분산
- 상위 레벨 노드는 자주 접근 → 캐시에 유지됨
- 캐시 히트율 향상
```

### 문제 2: 디스크 단편화
```
불균형 트리:
- 노드들이 한 방향으로만 연결
- 파일이 길게 늘어남
- 디스크 헤드가 큰 거리를 이동

균형 트리:
- 노드들이 트리 형태로 분산
- 상대적으로 더 나은 지역성
```

### 문제 3: 동시성 문제
```
불균형 트리:
- 모든 삽입이 한 경로를 따라감 (오른쪽)
- 병렬 처리 불가능
- Lock contention 심각

균형 트리:
- 삽입이 여러 경로로 분산
- 병렬 처리 가능
- Lock contention 감소
```

## 8. 결론: 왜 B-Tree가 필요한가

### Binary Search Tree의 한계
```
✗ 순차 데이터에 취약 (시간 순서, ID 등)
✗ 균형 보장 없음 - 운에 맡겨야 함
✗ 각 노드 접근마다 I/O 발생
✗ 노드당 2개의 포인터만 (왼쪽, 오른쪽)
```

### B-Tree의 해결책
```
✓ 자동 균형 유지 (항상 높이 = O(log N))
✓ 한 노드에 여러 키 저장 (100~200개)
✓ 노드 크기 = 페이지 크기 (4KB) → 한 번 읽으면 많은 정보
✓ 트리 높이 대폭 감소 (N=1,000,000 → 높이 3-4)
✓ 페이지 단위 I/O로 효율 극대화
```

### 성능 비교 예상치 (N=1,000,000)
```
BST 불균형:
- 높이: ~1,000,000
- 검색 I/O: 최악 1,000,000번
- 소요 시간: ~6,000초 (1.6시간!)

BST 균형:
- 높이: ~20
- 검색 I/O: 최악 20번
- 소요 시간: ~120ms

B-Tree (t=100):
- 높이: ~4
- 검색 I/O: 최악 4번 (하지만 각 노드에서 200개 키 탐색)
- 소요 시간: ~24ms + 메모리 탐색
```

## 핵심 요약

1. **디스크 I/O는 매우 느리다** - ms 단위
2. **불균형 트리는 높이가 N** - N번의 I/O
3. **균형 트리는 높이가 log N** - log N번의 I/O
4. **N=10,000일 때 307배 차이!**
5. **B-Tree는 균형 + 페이지 최적화** - 최고 성능

**데이터베이스가 B-Tree를 사용하는 이유:**
→ 디스크 I/O를 최소화하면서 균형을 자동으로 유지하기 때문!
